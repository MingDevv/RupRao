[บทที่ 2] venv คืออะไร (สร้างครั้งแรก 3 พ.ย.)
- venv = "ห้องแยกไลบรารีของแต่ละโปรเจกต์" กันโปรเจกต์อื่นชนกันเวอร์ชันไม่ตรง
- สร้าง: python3 -m venv venv  |  ใช้ของในนั้น: venv/bin/python หรือ venv/bin/pip
- โปรแกรมเมอร์จริงทำแบบนี้ทุกโปรเจกต์ ถือเป็นมารยาทพื้นฐาน

[บทที่ 3] ไลบรารี (pip)
- ไลบรารี = ชุดเครื่องมือที่คนอื่นเขียนไว้ให้ใช้ฟรี ไม่ต้องเขียนเองทุกอย่าง
- ติดตั้ง: venv/bin/pip install ชื่อไลบรารี
- ของที่โปรเจกต์นี้ใช้: opencv (จัดการรูป), numpy (คำนวณตัวเลข), onnxruntime (รันโมเดล AI),

- ทริค: บางทีต้องเลือกเวอร์ชัน เช่น "numpy<2" กันชนกับ insightface

[บทที่ 4] รูปภาพในสายตาคอมพิวเตอร์
- รูป = ตารางตัวเลขมหึมา (แต่ละพิกเซล = เลข 0-255 สามชุด: แดง เขียว น้ำเงิน)
- รูปทดสอบเรา 1300x420 = 546,000 ช่อง — AI ไม่มีตา อ่านตัวเลขล้วนๆ แล้วเดาว่ากลุ่มไหนคือ "หน้า"

[บทที่ 5] AI จับหน้า (Face Detection) ทำงานยังไง ⭐ หัวใจวันแรก
1) โมเดล SCRFD เคยดูหน้าคนนับล้านใบพร้อมคำตอบว่าหน้าอยู่ตรงไหน (supervised learning)
   มันไม่ได้รับกฎว่า "หน้า = ตา 2 จมูก 1" แต่เขียนกฎเองจากตัวอย่าง — นี่คือ Machine Learning
2) มองแบบมี "ชั้น" จากง่ายไปยาก: ขอบ/เส้น/เงา -> วงตา/จมูก/ปาก -> "โครงหน้ามนุษย์!"
3) ไล่สแกนทุกบริเวณของรูปย่อ 640px (ตัวแปร det_size) หลายสเกล ถามซ้ำ "ตรงนี้มีหน้ามั้ย?"
4) คำตอบไม่ใช่ ใช่/ไม่ใช่ แต่เป็น "คะแนนความมั่นใจ" 0.0-1.0 (เราได้ 0.81-0.88 มาแล้ว)
5) คนเป็นคนตั้งกติกาว่าตัดกันที่เท่าไหร่ (threshold ~0.5):
   ลดลง = เจอเยอะแต่หลอกเยอะ / เพิ่มขึ้น = เน้นชัวร์แต่พลาดหน้าเล็ก
   การจูนเลขนี้คือสกิลจริงของคนทำ ML — ตอนทำ RupRao จริงต้องจูนด้วยมือ
6) โมเดลยังหา "จุด landmark" ได้ (ตา คิ้ว จมูก ปาก รวม 106 จุด) ใช้จัดหน้าให้ตรง
   ก่อนขั้นต่อไป (ไฟล์ 2d106det.onnx ใน log ก็คือตัวนี้)
7) กรอบที่ซ้ำทับกัน ตัดให้เหลืออันที่มั่นใจสุด (เทคนิคชื่อ NMS)

[บทที่ 8] เมื่อเน็ตบล็อก: SSH กับ HTTPS

  (2) SSH ผ่านพอร์ต 443 แทน 22
- [อัปเดต 4 พ.ย.] เน็ตใหม่เปิดทาง SSH:443 ผ่าน แถม SSH key ถูกเพิ่มในบัญชี GitHub แล้ว
  (คีย์ใน ~/.ssh/ ชื่อ MingDevv@users.noreply.github.com) — push ผ่านทางนี้เรียบร้อย
  บทเรียน: อย่างน้อย 2 ทางเสมอ ถ้าทางนึงถูกบล็อก ลองอีกทางก่อนยอมแพ้

[บทที่ 10] push ขึ้น GitHub สำเร็จ + .ssh/config ⭐
- เชื่อม repo กับเครื่อง: git remote add origin git@github.com:MingDevv/RupRao.git
- push ครั้งแรก: git push -u origin main  (ตัว -u จำ "คู่บ้าน" ไว้ รอบหลังพิมพ์แค่ git push)
- ตั้งทางผ่านถาวรใน ~/.ssh/config:
    Host github.com
      HostName ssh.github.com
      Port 443
      User git
  → git ทุกคำสั่งวิ่งผ่านพอร์ต 443 เองโดยอัตโนมัติ ไม่ต้องจำทางเลื้อยอีก
- ถ้า repo ฝั่งเว็บมีไฟล์อยู่ก่อน push จะโดนปฏิเสธ ต้อง rebase --allow-unrelated-histories ก่อน
- แก้ชื่อผู้เขียน commit ย้อนหลัง: ตั้ง git config user.name/user.email แล้วใช้ git filter-branch
  ตามด้วย push --force (ใช้ได้เฉพาะ repo ที่ยังไม่มีคนอื่น pull ไป — ถ้ามีแล้วห้ามเด็ดขาด)

[บทที่ 11] Embedding — ลายเซ็นหน้า 512 ตัวเลข ⭐⭐ หัวใจของ RupRao
- โมเดล ArcFace (w600k_r50.onnx) เปลี่ยนหน้า 1 ใบ -> เวกเตอร์ 512 ตัวเลข
  (insightface คำนวณให้อัตโนมัติที่ face.embedding — จัดตำแหน่งหน้าจาก landmark ให้เองก่อนด้วย)
- หน้าคนเดียวกัน (มุมไหน แสงไหน) -> เวกเตอร์ "ทิศทาง" ใกล้เคียงกัน / คนละคน -> ทิศทางห่างไกล
- วัดความเหมือนด้วย cosine similarity (มุมระหว่างเวกเตอร์): 1.0 เหมือนสุด -> 0 ไม่เกี่ยว
- ผลทดลองจริงวันนี้: คนเดียวกันพลิกซ้ายขวา = 0.95 / คนละคน = -0.04  (ห่างกันสุดๆ แยกง่ายมาก)
- เกณฑ์เริ่มต้นของโปรเจกต์: >= 0.45 คนเดียวกัน, < 0.30 คนละคน (จะจูนจากข้อมูลจริงในเฟส 3)
- ไอเดียหลักของ ML จากบทนี้: "เปลี่ยนของยุ่ง (รูป) ให้เป็นตัวเลข แล้วคณิตง่ายๆ (มุม) ทำงานแม่นได้"
  เทคนิคเดียวกันกับระบบแนะนำเพลง/สินค้า และการค้นหาเชิงความหมายทั้งหลาย

[บทที่ 13] SQLite กับ FAISS ทำงานคู่กันยังไง ⭐ (สถาปัตยกรรม 2 ขา)
- SQLite (ไฟล์ faces.db) เก่งเรื่อง "ข้อความและตัวเลขทั่วไป":
  เก็บว่ารูปนี้ชื่ออะไร, อยู่โฟลเดอร์งานไหน, ขนาดเท่าไหร่, พิกัดกรอบหน้า (bbox) อยู่ตรงไหน
  แต่ SQLite ค้นหาเวกเตอร์ AI ไม่เป็น (ช้าและไม่มีสูตรคำนวณเวกเตอร์ในตัว)
- FAISS (ไฟล์ index.faiss) เก่งเรื่อง "ค้นหาเวกเตอร์ความเร็วแสง":
  พัฒนาโดยทีมวิจัย AI ของ Meta/Facebook เพื่อค้นหาเวกเตอร์นับล้านรายการในเสี้ยวของมิลลิวินาที
  แต่ FAISS ไม่เก็บข้อความหรือชื่อไฟล์ เก็บแค่ตัวเลข 512 มิติ กับตัวเลข ID
- สูตรผสาน: ผูกเวกเตอร์ใน FAISS ด้วย `faiss_id` ตัวเลขเดียวกับตาราง `faces` ใน SQLite
  เวลาค้น: เอาเซลฟี่โยนเข้า FAISS -> ได้ `faiss_id` ที่คะแนนสูงสุด -> เอา ID ไปเปิดดูชื่อรูปใน SQLite
  เร็วทั้งค้น และได้ข้อมูลครบถ้วน!

[บทที่ 14] L2 Normalization — เคล็ดลับคณิตศาสตร์เวกเตอร์
- ปกติเราวัดความเหมือนด้วย Cosine Similarity (มุมระหว่าง 2 เวกเตอร์)
- ใน FAISS โครงสร้างที่เร็วที่สุดคือ Inner Product (`IndexFlatIP`) หรือการคูณดอทตรงๆ
- ถ้าเราทำ "L2 Normalization" (หารเวกเตอร์ด้วยความยาวของตัวมันเองจนความยาว = 1.0) ก่อนเก็บ
  ผลคูณ Inner Product จะเท่ากับค่า Cosine Similarity พอดิบพอดีแบบ 100%!
  ทำให้ได้ทั้งความเร็วสูงสุดของฮาร์ดแวร์ CPU และได้ผลลัพธ์ที่เป็นเปอร์เซ็นต์ความเหมือนจริง

[บทที่ 17] FastAPI — สะพานเชื่อม Python AI กับเว็บเบราว์เซอร์ ⭐
- FastAPI เป็นเว็บเฟรมเวิร์กของ Python ที่เร็วมากและเขียนง่าย
- หน้าที่ของมันคือรับคำสั่งจากผู้ใช้ผ่าน HTTP Request แล้วส่งผลลัพธ์กลับเป็น JSON หรือรูปภาพ
- คำสั่งสำคัญ:
  - `POST /api/search` — รับรูปเซลฟี่เข้ามาคำนวณ
  - `GET /api/thumb/{id}` — ส่งรูปขนาดย่อมไปโชว์ในเบราว์เซอร์
  - `GET /api/download?ids=...` — ส่งไฟล์ ZIP กลับไปให้ผู้ใช้

[บทที่ 18] In-Memory Processing กับ กติกาความเป็นส่วนตัว (PDPA) ⭐⭐
- กติกาเหล็กข้อที่ 2 ของ RupRao: "รูปเซลฟี่ของคนค้นหา ห้ามเก็บลงดิสก์"
- วิธีทำด้วยโค้ด:
  1) รับไฟล์เข้ามาเป็นไบต์ใน RAM: `contents = await selfie.read()`
  2) แปลงไบต์เป็นภาพ OpenCV โดยตรง: `img = cv2.imdecode(np.frombuffer(contents, np.uint8), cv2.IMREAD_COLOR)`
  3) พอได้เวกเตอร์ 512 ตัวเลขเสร็จ ให้ล้างตัวแปรภาพทิ้งทันที: `del contents, img, faces`
- ไม่มีไฟล์ชั่วคราว (temp file) ตกค้างในฮาร์ดดิสก์เลยแม้แต่ไฟล์เดียว — ปลอดภัย 100% สบายใจเรื่องข้อมูลส่วนบุคคล

[บทที่ 19] สตรีมไฟล์ ZIP จาก RAM ให้ดาวน์โหลดในคลิกเดียว
- ปกติถ้าจะให้คนโหลด zip ต้องสร้างไฟล์ลงฮาร์ดดิสก์ก่อนแล้วค่อยส่ง
- แต่ใน RupRao เราใช้ `io.BytesIO()` สร้างไฟล์ ZIP จำลองขึ้นมาในหน่วยความจำ RAM
- เอาเฉพาะรูปที่ผู้ใช้เลือก (ติ๊กถูก) บีบอัดลง ZIP บัฟเฟอร์ แล้วส่งกลับด้วย `StreamingResponse`

[บทที่ 26] หลัก PDPA ในระบบค้นหาใบหน้า (Zero-Disk & Right to be Forgotten) ⭐⭐⭐
- กฎหมายคุ้มครองข้อมูลส่วนบุคคล (PDPA) ให้ความสำคัญอย่างยิ่งกับข้อมูลชีวมิติ (Biometric Data)
- RupRao ใช้หลักการออกแบบเพื่อความเป็นส่วนตัว (Privacy by Design):
  1) **Zero-Disk Retention:** รูปเซลฟี่ที่อัปโหลดจะถูกถอดรหัสใน RAM ชั่วคราว สกัดเวกเตอร์ 512 มิติ แล้วลบทิ้งทันที ไม่เคยมีรูปเซลฟี่แตะลงฮาร์ดดิสก์
  2) **Right to be Forgotten (สิทธิที่จะได้รับการลบ):** มีปุ่ม `🚩 ขอลบรูปนี้` บนการ์ดทุกใบ เพื่อให้นักเรียนขอลบรูปตนเองได้ตลอดเวลาตามสิทธิทางกฎหมาย

[บทที่ 29] กับดัก Path สัมพัทธ์ + พลังของการรัน test ซ้ำหลังแก้โค้ด ⭐⭐⭐ (4 พ.ย. ค่ำ)
- เรื่องจริง: รัน test_production.py ซ้ำ แล้วด่าน "ซ่อนรูป" พัง — สั่งซ่อนแล้วรูปยังโผล่ในผลค้นหา

  -> Python สร้าง "ฐานข้อมูลใหม่ว่างเปล่า" ขึ้นที่ผิดโดยไม่มี error เตือนเลยแม้แต่บรรทัดเดียว!
  คำสั่งซ่อนรูปวิ่งเข้าไฟล์ปริศนา (0 แถว) ส่วนเซิร์ฟเวอร์อ่านไฟล์จริงที่ไม่เคยถูกซ่อน
- วิธีจับ: ตามหาไฟล์ปริศนา (เจอ data/faces.db ข้างนอกโปรเจกต์) + ไล่ข้อมูลจริงใน DB
  (คำร้องยัง pending, is_hidden = 0 ทั้งที่ "สั่ง" ไปแล้ว) = พิสูจน์ด้วยของจริง ไม่เดา
- ทางแก้: ใช้ absolute path จาก BASE (Path(__file__).resolve().parent) เสมอ ในทุกไฟล์
- บทเรียนซ้อน: "แก้บั๊กเสร็จต้องรัน test ซ้ำ" — รอบนี้ test จับปัญหาได้ทันที
  และได้ฝึกจังหวะมืออาชีพ: snapshot DB ก่อนทดสอบ -> ทดสอบ -> คืนค่า/ให้ test เก็บกวาดเอง
- ข้อสังเกต: รอบแรกที่ test ผ่าน (คาบก่อน) ผ่านเพราะบังเอิญรันจาก cwd ที่ถูก
  บั๊กแบบนี้รอดการทดสอบได้นาน ถ้าไม่มีใครลองรันจากที่อื่น — test ที่ดีต้อง cwd-proof

[บทที่ 30] รายงานทดสอบความ sensitive รอบแรก ⭐⭐ (4 พ.ย. ค่ำ — โจทย์จากเพื่อน)
- หน้าตัวเอง (ming.jpeg): ตรง 100% | หน้าแปลกปลอม 3 คน: 0% ทุก threshold
  -> ไม่มี false positive แม้แต่ตัวเดียว แม้คลายกันถึง 0.30
- ระยะห่าง "ตัวเอง vs คนแปลก" = 100 จุด -> threshold 0.34-0.45 ปลอดภัยมาก
- หน้าเล็กจิว (~40px ในรูปงาน): ครอปแน่น+ขยาย 8 เท่า = เบลอจน detector มองไม่เห็น (422!)
  แต่ครอปเผื่อบริบทรอบข้าง ไม่ขยาย = ตรง 99%! -> detector อยากได้ "บริบทรอบข้าง" มากกว่า "ขนาดรูป"
- ย่อรูปงาน: เหลือ 25% (192px) ยังจับครบ 3 หน้า / เหลือ 12% (92px) เหลือ 2
  -> ขีดจำกัดการจับหน้าอยู่ราวๆ ตรงนี้ (สำหรับรูปงานขนาดนี้)
- กับดักรูปหมู่เป็น query: ระบบเลือกค้นด้วย "หน้าที่ detector มั่นใจสุด" เพียงหน้าเดียว
  พิสูจน์แล้ว: ใน d.jpeg หน้าเพื่อนได้ 0.90 (ถูกเลือก) แต่หน้า ming ได้ 0.77 (ไม่ถูกเลือก)
  เลยทำให้ "ค้นด้วย d.jpeg" ไม่เจอ ming.jpeg ส่วน "ค้นด้วย ming.jpeg" เจอ d.jpeg ที่ 73%
  -> ระบบจริงควรให้ผู้ใช้เลือกหน้าก่อนค้นเมื่อ query มีหลายหน้า (แผนเฟส 4 มีข้อนี้อยู่แล้ว)
- เครื่องมือใหม่: test_sensitivity.py รันซ้ำได้ทุกครั้งที่มีหน้าใหม่ (เช่น หน้าเก๊ หน้าน้อย)

[บทที่ 32] 200 OK ≠ งานสำเร็จ — บั๊ก "หลอกสำเร็จ" + งานเบื้องหลังที่ถูกต้อง ⭐⭐⭐ (4 พ.ย. ดึก)
